# L1 balance check uses `total` instead of `total - hold`, allowing bridge when free balance is insufficient

**Severity:** High  
**Confidence:** 72%  
**Affected:** bridgePrincipalFromL1, _sendL1Bridge

## Summary
The `_sendL1Bridge` function in MonetrixVault.sol validates L1 available balance using `spotBalance(...).total` without subtracting the `hold` field (funds locked in open orders or margin), allowing bridge operations to pass their balance check even when the actual free/transferable USDC on L1 is insufficient. Because `outstandingL1Principal` is decremented before the L1 bridge action executes, a silently-dropped L1 transfer creates a permanent accounting mismatch between L2 records and actual L1 state.

## Vulnerability Detail
In `MonetrixVault.sol`, the internal function `_sendL1Bridge` reads the L1 spot balance via `PrecompileReader.spotBalance(...)`, which returns a `SpotBalance` struct containing `total`, `hold`, and `entryNtl` fields. The function assigns `l1Available = spotBalance(...).total` and compares it against the requested bridge `amount`, but never subtracts `hold` — the portion of the balance locked in open hedge limit orders or margin requirements. The function's own NatSpec comment acknowledges the design intent to "avoid silent L1 drop when hedge is still locked," implicitly confirming that L1 silently drops bridge actions when free balance is insufficient rather than reverting the EVM transaction.

The critical ordering flaw is in the callers (`bridgePrincipalFromL1`, `bridgeYieldFromL1`, `emergencyBridgePrincipalFromL1`): they execute `outstandingL1Principal -= amount` *before* invoking `_sendL1Bridge`. When the L1 bridge action is silently dropped due to insufficient free balance, the L2 state has already been mutated — `outstandingL1Principal` is permanently decremented — but no corresponding USDC transfer occurs on L1. The `hold` field from `PrecompileReader.sol`'s `SpotBalance` struct is available and accessible but is entirely ignored in the sufficiency check.

## Impact
An operator (or compromised operator key) can trigger `bridgePrincipalFromL1` when the vault's L1 spot USDC has significant `hold` from open hedge positions or margin. For example, if L1 spot has `total=1000` USDC with `hold=800` (locked in orders), only 200 USDC is actually transferable, yet a bridge of 500 USDC passes the balance check. The L1 bridge action is silently dropped, but L2's `outstandingL1Principal` is decremented by 500. This breaks the L1↔L2 principal reconciliation invariant: L2 accounting records show that principal was returned to L1, but L1 never transferred it. The resulting accounting mismatch can mask fund shortfalls, cause redemption calculations to undercount available assets, and leave the protocol unable to accurately reconcile cross-chain balances — potentially leading to user fund loss during redemptions when the vault believes more principal has been repatriated than actually exists on L1.

## Recommendation
In `_sendL1Bridge` within `MonetrixVault.sol`, compute the available L1 balance by subtracting `hold` from `total`:

```solidity
SpotBalance memory bal = PrecompileReader.spotBalance(...);
uint256 l1Available = bal.total - bal.hold;
```

Additionally, add `suppliedBalance` only if those PM pool funds are also confirmed to be free (not locked as margin for open perp positions). Consider also reordering the state mutation so that `outstandingL1Principal -= amount` executes *after* `_sendL1Bridge` confirms the bridge action was successfully dispatched, or implement a return-value check from `_sendL1Bridge` that reverts the L2 state change if the L1 action would be silently dropped. This ensures the L2 accounting decrement only occurs when the L1 transfer is guaranteed to execute.
