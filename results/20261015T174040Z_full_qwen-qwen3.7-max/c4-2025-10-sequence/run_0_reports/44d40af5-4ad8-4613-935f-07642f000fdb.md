# Guest contract bypasses wallet auth, enabling unauthorized call dispatch

**Severity:** High  
**Confidence:** 82%  
**Affected:** Guest.fallback, Guest._dispatchGuest, Calls._execute, Calls.selfExecute

## Summary
The Guest contract's _dispatchGuest function lacks a guard against calls targeting the wallet address, allowing a session signer with Guest permissions to bypass SessionManager's InvalidSelfCall restriction and re-enter the wallet proxy to trigger registered hooks in the wallet's storage context.

## Vulnerability Detail
SessionManager.recoverSapientSignature() enforces a self-call restriction: `if (call.to == wallet) { revert SessionErrors.InvalidSelfCall(); }`. This check validates only the outer call's target. When the outer call targets the Guest contract (Guest ≠ wallet), the check passes. Guest._dispatchGuest() then decodes and dispatches nested calls via `LibOptim.call(call.to, ...)`, but only validates `if (call.delegateCall) { revert DelegateCallNotAllowed(i); }` — it has no equivalent check preventing `call.to == wallet`. A nested call from Guest to the wallet address hits the wallet proxy's fallback, which delegatecalls to the module. The module's Hooks fallback reads registered hooks via `_readHook(bytes4(msg.data))` and, if a hook is registered for the selector, executes it via `target.delegatecall(msg.data)` in the wallet's storage context. While `onlySelf`-protected functions (selfExecute, addHook, updateImplementation) remain safe because msg.sender = Guest ≠ wallet, the design intent of InvalidSelfCall is to prevent ANY session-signed re-entry into the wallet, and Guest provides an unguarded bypass channel.

## Impact
A session signer granted permission to call the Guest contract can craft nested calls that re-enter the wallet proxy and trigger any registered hook. If a hook performs state-changing operations (e.g., token transfers, permission updates, or implementation changes) without its own authorization checks beyond assuming wallet-context execution, the attacker can execute those operations outside the intended session scope. This undermines the session security model's core guarantee that self-calls are blocked, potentially allowing unauthorized asset movement or privilege escalation depending on which hooks are registered.

## Recommendation
Add a wallet-target check in Guest._dispatchGuest() mirroring SessionManager's InvalidSelfCall guard. Before dispatching each nested call, verify that `call.to` is not the wallet address: `if (call.to == wallet) { revert InvalidSelfCall(); }`. This requires Guest to know the wallet address, which can be passed as a parameter to the Guest fallback or stored during initialization. Alternatively, enforce the check at the Calls._execute level by recursively validating that no nested call within a Guest-dispatched batch targets the wallet. The first approach (guard in Guest) is preferred as it is defense-in-depth and does not rely on the caller performing validation.

## Skeptic Notes
The vulnerability is confirmed by source code analysis. The attack path is:

1. SessionManager.recoverSapientSignature() explicitly blocks self-calls: `if (call.to == wallet) { revert SessionErrors.InvalidSelfCall(); }` — this is the protection the hypothesis targets.

2. Guest._dispatchGuest() only blocks delegate calls (`if (call.delegateCall) { revert DelegateCallNotAllowed(i); }`) but has NO equivalent check for calls targeting the wallet address. It dispatches arbitrary calls via `LibOptim.call(call.to, ...)`.

3. When a session signer has permission to call Guest (target = Guest ≠ wallet), SessionManager's InvalidSelfCall check passes for the outer call. Guest then forwards nested calls to any address, including the wallet itself.

4. The nested call from Guest to the wallet hits the wallet proxy's fallback, which delegatecalls to the module. The module's Hooks fallback then checks for registered hooks: `address target = _readHook(bytes4(msg.data)); if (target != address(0)) { target.delegatecall(msg.data); }`. If a hook is registered for the selector, it executes in the wallet's storage context.

5. While `onlySelf`-protected functions (selfExecute, addHook, updateImplementation, etc.) are safe because msg.sender = Guest ≠ wallet, the design intent of SessionManager's InvalidSelfCall is clearly to prevent ANY re-entry into the wallet from session-signed transactions. Guest provides a bypass channel.

The PoC failed to compile due to a variable shadowing error (`Guest Guest;` shadows the contract name), which is a test setup issue, not a vulnerability invalidation. The source code clearly shows the missing guard in Guest that SessionManager has.

The attack requires: (a) session signer has permission to call Guest, (b) a hook is registered on the wallet that can be triggered. These are plausible preconditions in a real deployment.
