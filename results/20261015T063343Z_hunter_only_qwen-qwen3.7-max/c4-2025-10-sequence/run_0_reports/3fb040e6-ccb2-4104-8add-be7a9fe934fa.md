### SessionManager view-only validation allows TOCTOU on usage limits across batched calls

**Severity (estimated):** Medium  
**Confidence:** 0%  
**Affected:** SessionManager.recoverSapientSignature, ExplicitSessionManager._validateExplicitCall, ExplicitSessionManager._validateLimitUsageIncrement, ExplicitSessionManager.incrementUsageLimit, PermissionValidator.validatePermission

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. SessionManager.recoverSapientSignature() is a `view` function called during signature validation in BaseAuth.signatureValidation().
2. During this view call, it computes expected usage limit increments and validates them against the current state.
3. It expects the first call in the payload to be incrementUsageLimit() which will persist the new limits.
4. However, the view validation reads `getLimitUsage()` from storage, computes expected new values, and returns.
5. During actual execution in Calls._execute(), if any call BEFORE incrementUsageLimit modifies the limitUsage storage (e.g., via a hook delegatecall or a call to another contract that calls back to incrementUsageLimit), the pre-validated limits become stale.
6. The incrementUsageLimit call then writes values that were validated against stale state, potentially allowing usage limit bypass.
7. The SessionManager bans ABORT_ON_ERROR but does not ban IGNORE_ERROR for the increment call itself, and the onlyFallback check in _validateLimitUsageIncrement can be bypassed if the preceding call fails with IGNORE_ERROR.

**Skeptic notes:** Not validated: SKEPTIC_ENABLED=false.
