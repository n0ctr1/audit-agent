### recover: Checkpointer address read from signature data when _checkpointer is address(0) enables imageHash manipulation in chained signatures

**Severity (estimated):** High  
**Confidence:** 0%  
**Affected:** recover, recoverChained

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. In recoverChained, for all signatures except the last, `checkpointer` is set to `address(0)`.
2. When recover() is called with `_checkpointer = address(0)` and the signature flag has bit 0x40 set, the checkpointer address is read FROM THE SIGNATURE DATA itself: `(_checkpointer, rindex) = _signature.readAddress(rindex)`.
3. Since `_ignoreCheckpointer` is true, the checkpointer's snapshotFor() is NOT called, but the attacker-chosen checkpointer address IS included in the imageHash: `imageHash = LibOptim.fkeccak256(imageHash, bytes32(uint256(uint160(_checkpointer))))`.
4. An attacker can embed different checkpointer addresses in different chained signature links, producing different imageHashes than what the legitimate signers intended.
5. This allows the attacker to make a chained signature's imageHash NOT match the on-chain stored imageHash, potentially bypassing snapshot validation or creating a configuration that appears valid under one checkpointer but is evaluated under another.
6. Since the checkpointer is never actually called (ignoreCheckpointer=true), the attacker doesn't need the checkpointer to be a real contract - any address can be used to manipulate the imageHash.
