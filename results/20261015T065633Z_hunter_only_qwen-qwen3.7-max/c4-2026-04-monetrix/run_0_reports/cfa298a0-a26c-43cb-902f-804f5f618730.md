### RedeemEscrow totalOwed can be set without collateralization check, enabling underfunded redemption queue

**Severity (estimated):** High  
**Confidence:** 0%  
**Affected:** RedeemEscrow.addObligation, RedeemEscrow.payOut, RedeemEscrow.reclaimTo, MonetrixVault.requestRedeem

**Attack scenario:** 1. Vault.requestRedeem calls RedeemEscrow.addObligation(amount) to record a new redemption obligation. 2. addObligation increments totalOwed WITHOUT checking whether the Escrow actually holds sufficient USDC to cover the new total. 3. If the Vault has a bug or is manipulated into calling addObligation with amounts exceeding available USDC, totalOwed exceeds the Escrow's actual balance. 4. The reclaimTo guard (bal >= amount + totalOwed) now prevents ANY reclamation because totalOwed alone exceeds bal — even though the excess obligation is phantom. 5. Meanwhile, payOut will revert on 'insufficient liquidity' for legitimate claimants. 6. The Escrow is effectively frozen: users cannot claim (no liquidity), Vault cannot reclaim (totalOwed too high). The only recovery is for someone to deposit USDC into the Escrow to cover the shortfall. This is a cross-contract issue because the invariant (totalOwed <= balance) depends on BOTH the Vault correctly funding the Escrow AND the Escrow's addObligation not verifying collateralization.
