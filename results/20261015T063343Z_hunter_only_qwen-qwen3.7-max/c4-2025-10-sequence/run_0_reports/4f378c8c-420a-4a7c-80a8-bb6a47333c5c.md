### Stage1Auth one-way upgrade to Stage2Module creates permanent validation bypass window

**Severity (estimated):** High  
**Confidence:** 0%  
**Affected:** Stage1Auth._updateImageHash, Stage1Auth._isValidImage, Stage2Auth._isValidImage, Implementation._updateImplementation

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Stage1Auth._isValidImage() validates imageHash by computing CREATE2(FACTORY, imageHash, INIT_CODE_HASH) and comparing to address(this). This ties the wallet to a specific Factory and mainModule.
2. When updateImageHash() is called, Stage1Auth writes the new imageHash AND upgrades the implementation to STAGE_2_IMPLEMENTATION in the same transaction.
3. Stage2Auth._isValidImage() simply checks `_imageHash == Storage.readBytes32(IMAGE_HASH_KEY)` - it no longer validates against the Factory or CREATE2 address.
4. After upgrade, any imageHash can be set (including ones that don't correspond to the original Factory-deployed address), because Stage2Auth dropped the CREATE2 validation.
5. If an attacker can get the wallet to call updateImageHash with a crafted imageHash that includes them as a signer, they gain full control.
6. The upgrade is one-way and irreversible - there is no mechanism to downgrade back to Stage1Auth's stricter validation.
