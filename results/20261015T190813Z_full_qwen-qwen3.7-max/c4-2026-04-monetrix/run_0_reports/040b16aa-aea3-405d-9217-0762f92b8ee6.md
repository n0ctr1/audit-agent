### Double-counting of spot hedge token balances inflates totalBackingSigned, allowing excess yield declaration

**Severity (estimated):** High  
**Confidence:** 55%  
**Affected:** _readL1Backing, totalBackingSigned, settleDailyPnL

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. The vault holds spot hedge tokens (e.g., spot BTC) on HyperCore L1 as part of a delta-neutral hedge (long spot + short perp).
2. The `accountValueSigned` precompile (0x80F) returns the signed aggregate margin value of the perp account, which typically includes the mark-to-market value of spot positions used as collateral in a portfolio margin setup.
3. `_readL1Backing` first adds `_readPerpAccountValueSigned(account)` (which may already include spot hedge token value), then iterates `cfg.tradeableAssets()` and adds `_readSpotAssetUsdc(spotIndex, perpIndex, account)` for each whitelisted asset — reading the same spot balances via the 0x801 precompile.
4. If the perp account value already reflects these spot positions, the spot hedge token value is counted twice in `totalBackingSigned()`.
5. This inflates `surplus()` and `distributableSurplus()`, allowing the vault to call `settleDailyPnL` with a `proposedYield` that exceeds the true economic surplus.
6. The excess yield is then distributed to sUSDM stakers, diluting USDM backing below 1:1.

Timeline: Operator notices inflated surplus → calls settleDailyPnL with inflated proposedYield → yield is injected into sUSDM → sUSDM exchange rate rises based on phantom backing → next redeemer receives USDC that isn't actually backed.

**Skeptic notes:** The vulnerability hinges entirely on external protocol behavior: whether HyperCore's 0x80F accountValueSigned precompile includes spot hedge token values in its aggregate return. The Monetrix source code clearly adds both (1) the 0x80F aggregate value AND (2) individual spot balances via 0x801 for each tradeable asset, with no deduplication logic. If 0x80F includes spot collateral (as is common in portfolio margin), double-counting is confirmed. If 0x80F only returns perp PnL, there is no bug. The source code comments describe 0x80F as "Perp account value (signed, 6-dp)" which is ambiguous — it could mean the perp account's total value (including collateral) or just perp position PnL. This is an external-contract behavior question that cannot be resolved from source code alone. The PoC failed to compile, providing no additional evidence. No concrete guard exists in the code to prevent double-counting if the precondition holds. The refuter stage must determine the actual semantics of the 0x80F precompile in portfolio margin mode.
