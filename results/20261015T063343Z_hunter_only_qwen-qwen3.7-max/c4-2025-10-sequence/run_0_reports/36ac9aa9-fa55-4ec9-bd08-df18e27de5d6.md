### Attack chain: Weight Inflation + Sapient Memory Mutation Leak Unauthorized Wallet Access

**Severity (estimated):** High  
**Confidence:** 70%  
**Affected:** recoverBranch, recoverSapientSignature

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Attacker observes a valid multi-sig transaction with a branch signature blob where signers have specific weights encoded in the signature (e.g., lower nibble of flag byte). The weight field is NOT included in _opHash (H2). 2. Attacker modifies the signature blob, inflating the weight of a single signer they control from 1 to a value that meets the threshold (e.g., from 1 to 10 when threshold is 10). Since weight is unsigned, recoverBranch accepts the inflated weight without invalidating the signature. 3. recoverBranch calls recoverSapientSignature on a sapient contract in the signature tree. Inside this call, the sapient contract mutates the _payload in memory (H14). The mutated payload — containing modified parentWallets data — leaks back to the caller. 4. When a second sapient contract B is processed in the same signature tree, it receives the already-mutated payload from step 3. The leaked parentWallets modifications can grant the attacker unauthorized access to parent wallet operations or bypass authorization checks in sapient B. 5. H2 alone inflates weight but doesn't leak data; H14 alone mutates memory but requires valid signature context. Together, weight inflation provides the entry point and memory mutation propagates unauthorized state changes.

Chain steps:
  1. recoverBranch: Attacker inflates weight of controlled signer in signature blob (unsigned field not in _opHash) → Inflated weight meets threshold, signature passes validation with attacker-controlled signer
  2. recoverSapientSignature (called from recoverBranch for sapient A): Sapient A processes the signature and mutates _payload in memory → Modified parentWallets data leaks into shared memory space
  3. recoverSapientSignature (called for sapient B in same transaction): Sapient B receives already-mutated payload from step 2 → Leaked parentWallets modifications bypass authorization in sapient B, granting unauthorized wallet operations

Root cause: Unsigned weight field in recoverBranch allows threshold manipulation, and memory mutation in recoverSapientSignature leaks modified state to subsequent calls in the same transaction
