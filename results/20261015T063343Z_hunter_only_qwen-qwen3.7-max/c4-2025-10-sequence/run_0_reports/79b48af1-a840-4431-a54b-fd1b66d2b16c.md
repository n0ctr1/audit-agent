### Hooks fallback delegatecall allows hook contracts to hijack Wallet proxy implementation slot

**Severity (estimated):** Critical  
**Confidence:** 0%  
**Affected:** Hooks.fallback, Hooks.addHook, Implementation._setImplementation, Wallet proxy (sstore at address())

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. The Wallet proxy stores its implementation address at storage slot = address(this) (the proxy's own address), per the Huff constructor: `sstore(address(), _imp)`.
2. Hooks.addHook() writes hook addresses to storage at keccak256(HOOKS_KEY, selector).
3. Hooks.fallback() reads a hook address and performs delegatecall to it with arbitrary msg.data.
4. A malicious hook contract (or a legitimate hook with a vulnerability) can execute `sstore(proxyAddress, maliciousImplementation)` during the delegatecall, overwriting the proxy's implementation pointer.
5. All subsequent calls to the wallet will delegatecall to the attacker's implementation, giving full control over the wallet and all its assets.
6. Since addHook is onlySelf, the attacker needs the wallet to approve adding the malicious hook - but a hook with a subtle vulnerability could be added legitimately and then exploited later.
