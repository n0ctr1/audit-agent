### Guest and Calls inconsistent delegateCall handling enables bypass via fallback dispatch

**Severity (estimated):** Medium  
**Confidence:** 0%  
**Affected:** Guest._dispatchGuest, Calls._execute, Guest.fallback

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Guest._dispatchGuest() explicitly reverts on delegateCall: `if (call.delegateCall) revert DelegateCallNotAllowed(i)`.
2. Calls._execute() allows delegateCall and forwards to IDelegatedExtension.handleSequenceDelegateCall.
3. If Guest is used as a fallback handler for the wallet (e.g., via Hooks or direct fallback), an attacker can route calls through Guest that should be restricted, or route calls through Calls that Guest was meant to restrict.
4. Specifically, if a session signer's permissions are validated assuming Guest's restrictions (no delegatecall), but execution happens through Calls (which allows delegatecall), the session signer can execute delegatecalls that were assumed to be impossible.
5. This creates an assumption mismatch: SessionManager validates calls assuming certain restrictions that differ between Guest and Calls execution paths.
