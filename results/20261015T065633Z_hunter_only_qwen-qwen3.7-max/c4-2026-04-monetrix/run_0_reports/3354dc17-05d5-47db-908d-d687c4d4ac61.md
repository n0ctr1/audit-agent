### Double-counting of spot USDC between perp account value (0x80F) and explicit spot reads (0x801) inflates totalBackingSigned

**Severity (estimated):** Critical  
**Confidence:** 0%  
**Affected:** totalBackingSigned, _readL1Backing, distributableSurplus, surplus

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. The Accountant calls totalBackingSigned() which calls _readL1Backing(vault, vaultSupplied).
2. _readL1Backing first reads _readPerpAccountValueSigned(account) via PRECOMPILE_ACCOUNT_MARGIN_SUMMARY (0x80F). On Hyperliquid, the margin summary for cross-margin accounts includes the full account equity — spot wallet balances, supplied collateral, and unrealized perp PnL are all rolled into the signed account value.
3. _readL1Backing then ADDITIONALLY reads _readSpotUsdcBalance(account) via PRECOMPILE_SPOT_BALANCE (0x801) and adds it to total.
4. It then iterates suppliedList and adds suppliedBalance (0x811) for each registered slot — also already reflected in the 0x80F cross-margin equity.
5. If 0x80F indeed includes spot and supplied balances (standard for Hyperliquid cross-margin), the same USDC is counted twice: once inside the perp account value and once as an explicit addition.
6. This inflates totalBackingSigned, which inflates surplus(), which inflates distributableSurplus().
7. The Vault's settleDailyPnL Gate 3 (proposedYield ≤ distributableSurplus) would then allow yield declaration backed by phantom surplus — USDC that doesn't actually exist.
8. An operator or attacker who can trigger settleDailyPnL could extract yield that exceeds actual protocol profits, draining the vault over time.
