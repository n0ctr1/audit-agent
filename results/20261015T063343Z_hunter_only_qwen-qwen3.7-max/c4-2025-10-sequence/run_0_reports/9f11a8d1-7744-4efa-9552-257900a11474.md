### Hash collision in _leafForSapient via abi.encodePacked with bytes32 prefix string

**Severity (estimated):** Low  
**Confidence:** 0%  
**Affected:** BaseSig._leafForSapient, BaseSig._leafForAddressAndWeight

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. _leafForSapient computes keccak256(abi.encodePacked('Sequence sapient config:\n', _addr, _weight, _imageHash)).
2. While _addr (20 bytes), _weight (32 bytes), and _imageHash (32 bytes) are all fixed-length, the string literal 'Sequence sapient config:\n' is 25 bytes and 'Sequence signer:\n' is 16 bytes.
3. An attacker controlling _addr and _weight in _leafForAddressAndWeight could attempt to craft values such that the packed encoding of ('Sequence signer:\n', addr, weight) collides with a packed encoding of ('Sequence sapient config:\n', addr', weight', imageHash') from _leafForSapient.
4. Since the prefix strings differ in length (16 vs 25 bytes) and all subsequent fields are fixed-width, a direct cross-function collision requires the 16-byte prefix + 20-byte addr + first 9 bytes of weight to equal the 25-byte prefix + first 20 bytes of addr', which is computationally infeasible.
5. However, if additional leaf types are added in the future with different-length prefixes but overlapping field layouts, the use of abi.encodePacked without a delimiter or type tag becomes exploitable. This is a design-level weakness.
