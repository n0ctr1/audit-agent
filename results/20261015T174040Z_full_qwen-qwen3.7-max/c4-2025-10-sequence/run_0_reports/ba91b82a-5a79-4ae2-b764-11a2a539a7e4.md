# Snapshot bypass via intermediate imageHash match skips checkpoint validation in recoverChained

**Severity:** High  
**Confidence:** 90%  
**Affected:** recoverChained

## Summary
The `recoverChained` function in `BaseSig.sol` contains a logic flaw where an intermediate chain link whose `imageHash` matches the on-chain snapshot causes the snapshot's `imageHash` to be zeroed, which in turn causes the final checkpoint regression guard to be short-circuit skipped. This allows an attacker to craft a chained signature that reverts the wallet to an older, attacker-controlled configuration with a lower checkpoint, bypassing snapshot-based replay protection.

## Vulnerability Detail
In `BaseSig.recoverChained()`, the function iterates over a chain of signatures. When a link's recovered `imageHash` matches `_snapshot.imageHash`, the snapshot is consumed by setting `_snapshot.imageHash = bytes32(0)`. After the loop, the final validation check is:

```solidity
if (_snapshot.imageHash != bytes32(0) && checkpoint <= _snapshot.checkpoint) revert UnusedSnapshot(_snapshot);
```

This uses a short-circuit AND operator. Once an intermediate link zeroes `_snapshot.imageHash`, the first operand evaluates to `false`, and the entire checkpoint comparison (`checkpoint <= _snapshot.checkpoint`) is never evaluated. The strictly-decreasing checkpoint ordering between consecutive links is enforced within the loop, but there is no check that the final link's checkpoint is greater than or equal to the snapshot's checkpoint once the snapshot has been consumed. An attacker can therefore construct a chain such as: Link 1 (checkpoint=200, imageHash=A) → Link 2 (checkpoint=150, imageHash=X, matching the on-chain snapshot, causing `_snapshot.imageHash` to be zeroed) → Link 3 (checkpoint=50, imageHash=Y). The chain passes all intra-link ordering checks (200 > 150 > 50), the snapshot is consumed at Link 2, and the final guard is skipped entirely, accepting imageHash=Y at checkpoint=50 even though the wallet's snapshot had checkpoint=100.

## Impact
An attacker who can obtain or construct valid chained signatures (with sufficient signer weight at each link) can revert the wallet to any historical configuration with a lower checkpoint. If the attacker was a signer (or controls signers with sufficient threshold weight) in that older configuration, they gain full control over the wallet and can execute arbitrary transactions, drain funds, and modify the wallet's configuration permanently. This affects all wallet instances that use a checkpointer providing snapshot-based replay protection and rely on `recoverChained` for configuration updates or recovery flows.

## Recommendation
Decouple the snapshot consumption from the checkpoint regression check. Store the snapshot's checkpoint in a local variable before the loop begins, and after the loop, independently verify that the final chain checkpoint is not less than the snapshot's checkpoint regardless of whether the snapshot's imageHash was consumed. For example:

```solidity
uint256 snapshotCheckpoint = _snapshot.checkpoint;
// ... loop that may zero _snapshot.imageHash ...
if (checkpoint < snapshotCheckpoint) revert CheckpointRegression(checkpoint, snapshotCheckpoint);
if (_snapshot.imageHash != bytes32(0)) revert UnusedSnapshot(_snapshot);
```

This ensures that even when an intermediate link consumes the snapshot by matching its imageHash, the final checkpoint is still validated against the snapshot's checkpoint, preventing regression to older configurations.

## Skeptic Notes
The vulnerability is clearly visible in the source code of BaseSig.recoverChained(). When an intermediate chain link's imageHash matches _snapshot.imageHash, the snapshot's imageHash is zeroed (`_snapshot.imageHash = bytes32(0)`). The final validation check `if (_snapshot.imageHash != bytes32(0) && checkpoint <= _snapshot.checkpoint)` uses a short-circuit AND, so when imageHash is zeroed, the entire checkpoint regression check is skipped. This allows a chained signature to pass through the current config (consuming the snapshot) and then regress to an older configuration with a lower checkpoint. The checkpoint ordering check (strictly decreasing) only applies between consecutive links, not against the snapshot's checkpoint. No other guard in the function prevents this bypass. The PoC failed due to missing environment variables (unrelated to the vulnerability), but the source code confirms the logic flaw.
