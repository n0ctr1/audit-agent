### recoverSapientSignature: memory payload mutation leaks modified parentWallets to subsequent sapient calls in same transaction

**Severity (estimated):** Medium  
**Confidence:** 0%  
**Affected:** recoverSapientSignature, recoverBranch

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. A signature tree contains two FLAG_SIGNATURE_SAPIENT entries pointing to sapient contracts A and B.
2. recoverBranch processes sapient A first: calls ISapient(A).recoverSapientSignature(_payload, sig_A).
3. Inside recoverSapientSignature on contract A, _payload.parentWallets is mutated in memory to append msg.sender (the wallet address).
4. Since _payload is passed as `memory` (not `calldata`), this mutation persists in the calling context's memory.
5. When recoverBranch processes sapient B, it calls ISapient(B).recoverSapientSignature(_payload, sig_B) with the ALREADY-MODIFIED _payload that now includes the wallet address in parentWallets.
6. Sapient contract B validates against a payload with an extra parentWallet that wasn't in the original configuration, potentially causing it to compute a different imageHash than intended.
7. If B's validation logic depends on the exact set of parentWallets (e.g., for domain separation or multi-wallet authorization), this could lead to incorrect validation results.
