### HLP vault equity unit mismatch: raw uint64 added without L1→EVM decimal conversion

**Severity (estimated):** Critical  
**Confidence:** 0%  
**Affected:** MonetrixAccountant._readHlpEquity, MonetrixAccountant._readL1Backing, MonetrixAccountant.totalBackingSigned, MonetrixAccountant.surplus

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. The protocol's L1 precompiles consistently use 8dp for USDC-denominated values (spot balances, supplied balances). The code explicitly converts these via usdcL1WeiToEvm (÷100) before adding to the backing total.
2. _readHlpEquity() reads vaultEquity from the HLP_VAULT precompile (0x802) and returns the raw uint64 equity value with NO decimal conversion.
3. If HLP vault equity is denominated in L1 8dp (consistent with other L1 precompile USDC values), it is added at 100× its true 6dp EVM value.
4. This inflates totalBackingSigned() by up to 99× the actual HLP equity.
5. surplus() = totalBackingSigned() - usdm.totalSupply() becomes massively overstated.
6. Attacker (or keeper) calls settleDailyPnL with a proposedYield that passes Gate 3 (proposedYield ≤ distributableSurplus) only because surplus is inflated by the unconverted HLP equity.
7. Yield is declared and distributed from funds that don't actually exist in backing, creating an insolvent position that will be discovered when HLP is withdrawn or a redemption wave hits.
