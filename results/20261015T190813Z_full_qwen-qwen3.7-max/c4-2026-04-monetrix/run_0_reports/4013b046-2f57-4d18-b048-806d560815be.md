# Same-block USDM minting inflates APR cap in settleDailyPnL allowing excess yield extraction

**Severity:** Medium  
**Confidence:** 82%  
**Affected:** settleDailyPnL, totalBackingSigned, _readL1Backing

## Summary
The APR cap (Gate 4) in `settleDailyPnL` is computed from `usdm.totalSupply()`, a same-block mutable value. A vault operator can inflate USDM supply via a large deposit in the same block as settlement, artificially raising the cap and extracting yield beyond the intended `maxAnnualYieldBps` rate limit.

## Vulnerability Detail
In `MonetrixVault.sol`, the `settleDailyPnL` function enforces four gates before approving yield distribution. Gate 4 computes an APR cap as:

```solidity
cap = (usdm.totalSupply() * maxAnnualYieldBps * elapsed) / (10_000 * 365 days)
```

This calculation reads `usdm.totalSupply()` (defined in `USDM.sol`) as a live, same-block snapshot with no time-weighted averaging, lagging, or checkpointing mechanism. Because `totalSupply()` increases immediately upon any `deposit()` call that mints USDM, an operator who controls vault settlement can execute a large deposit in the same block (or same transaction batch) before calling `settle()`, inflating the supply figure used in the cap formula.

Critically, Gate 3 (`distributableSurplus()`) is not similarly inflated by a deposit: `surplus = totalBackingSigned() - usdm.totalSupply()`, and both `totalBackingSigned()` (in `MonetrixAccountant.sol`, which aggregates EVM USDC balances via `usdc.balanceOf(vault)`, L1 spot balances via `_readL1Backing`, perp account values, and supplied balances) and `totalSupply()` increase by the same amount, leaving the surplus unchanged. However, Gate 4 depends solely on `totalSupply()`, so it is independently and directly inflated.

When Gate 4 is the binding constraint — which occurs when accumulated surplus is large relative to organic USDM supply (e.g., early protocol stage, post-redemption periods, or after sustained L1 yield accumulation with low minting activity) — inflating `totalSupply()` by a factor of N directly relaxes the cap by the same factor N, allowing `proposedYield` values up to N× the intended limit to pass validation.

The `onlyOperator` modifier on `vault.settle()` does not mitigate this: the operator is the identified threat actor, and no code-level guard prevents same-block supply manipulation from affecting the cap calculation.

## Impact
A vault operator (or colluding party with operator access) can extract yield significantly exceeding the protocol's intended `maxAnnualYieldBps` annualized rate limit. The excess yield is drawn from the accumulated distributable surplus and distributed to yield recipients under the operator's control. The attack is most impactful when organic USDM supply is small relative to accumulated surplus — for example, during early protocol deployment, after large redemption waves, or when L1 backing yield has accumulated without proportional USDM minting. In the worst case, the operator could extract the entire distributable surplus in a single settlement by inflating supply sufficiently, draining yield reserves that were intended to be distributed gradually over time according to the rate-limiting policy.

    // 3. [T=0] In the same block, attacker (operator) calls vault.settle() with a proposedYield that would normally fail Gate 4 (APR cap).
    // 4. [T=0] Because totalSupply is inflated, the cap is inflated, and the settlement succeeds.

        super.setUp();

        uint256 depositAmount = 100_000_000 * 1e6; // 100M USDC

        vm.startPrank(operator);
        usdc.approve(address(vault), depositAmount);
        
        // Get initial USDM supply
        uint256 initialSupply = usdm.totalSupply();
        console.log("Initial USDM supply:", initialSupply);

        vault.deposit(depositAmount);

        assertGt(inflatedSupply, initialSupply, "USDM supply should be inflated");

        // Advance time to pass minSettlementInterval
        vm.warp(block.timestamp + 1 days);
        
        // Get maxAnnualYieldBps from config
        uint256 maxBps = config.maxAnnualYieldBps();
        console.log("maxAnnualYieldBps:", maxBps);
        
        // Calculate a proposed yield that is way above the organic cap but passes the inflated cap
        // The cap is roughly (inflatedSupply * maxBps / 10000) / 365
        uint256 organicCap = (initialSupply * maxBps / 10000) / 365;
        uint256 inflatedCap = (inflatedSupply * maxBps / 10000) / 365;
        
        uint256 proposedYield = inflatedCap; 
        console.log("Proposed yield:", proposedYield);
        
        // Ensure proposedYield is greater than organicCap
        assertGt(proposedYield, organicCap, "Proposed yield should exceed organic cap");
        
        // Settle the daily PnL
        // vault.settle calls accountant.settleDailyPnL
        vault.settle(proposedYield);
        
        // Verify that the yield was settled
        uint256 totalSettled = accountant.totalSettledYield();
        console.log("Total settled yield:", totalSettled);
        
        assertGt(totalSettled, organicCap, "Settled yield should exceed organic cap due to inflated supply");
        
        vm.stopPrank();
    }
}

## Recommendation
Replace the same-block `usdm.totalSupply()` snapshot in Gate 4 with a time-weighted or lagged supply metric that cannot be manipulated within a single block. Specific approaches:

1. **Checkpoint-based supply**: Store a `lastSettlementSupply` variable updated at each successful `settleDailyPnL` call, and use this lagged value (rather than live `totalSupply()`) in the cap calculation. This ensures the cap reflects the supply that existed over the elapsed settlement period, not a same-block inflated value.

```solidity
// In MonetrixVault.sol, add state variable:
uint256 public lastSettlementSupply;

// In settleDailyPnL, replace:
// cap = (usdm.totalSupply() * maxAnnualYieldBps * elapsed) / (10_000 * 365 days)
// with:
uint256 supplyForCap = lastSettlementSupply > 0 ? lastSettlementSupply : usdm.totalSupply();
cap = (supplyForCap * maxAnnualYieldBps * elapsed) / (10_000 * 365 days);

// At the end of successful settlement:
lastSettlementSupply = usdm.totalSupply();
```

2. **Time-weighted average supply (TWAS)**: Accumulate `supply × time` in a cumulative counter and derive the average supply over the settlement interval, making single-block spikes negligible.

3. **Minimum holding period**: Require that any newly minted USDM does not count toward the cap calculation until at least one full settlement interval has elapsed, by tracking mint timestamps per-account or globally.

Option 1 is the simplest and most gas-efficient fix that directly addresses the root cause.

## Skeptic Notes
The vulnerability is confirmed in the source code. Gate 4 of `settleDailyPnL` computes the APR cap as:

```
cap = (usdm.totalSupply() * maxAnnualYieldBps * elapsed) / (10_000 * 365 days)
```

This uses `usdm.totalSupply()` which is a same-block mutable snapshot. An attacker (or any user with USDC) can call `vault.deposit()` to mint USDM and inflate totalSupply within the same block/transaction before `settle()` is called.

Critically, while Gate 3 (`distributableSurplus()`) is NOT inflated by a deposit (because `surplus() = totalBackingSigned() - usdm.totalSupply()` and both backing and supply increase equally), Gate 4 IS independently inflated since it depends only on totalSupply. When Gate 4 is the binding constraint (which occurs when surplus is large relative to supply — e.g., early protocol with accumulated L1 yield but small USDM supply), inflating totalSupply directly relaxes the cap and allows a larger `proposedYield` to pass.

The PoC failed to compile due to a test harness issue (`override` on `setUp()` without a parent to override), which is irrelevant to the vulnerability's existence. The source code clearly shows the pattern: a mutable same-block value (`usdm.totalSupply()`) is used as the basis for a rate-limiting cap without any time-weighting, lagging, or snapshot mechanism.

The operator role requirement (`onlyOperator` on `vault.settle()`) is a valid access control but doesn't prevent the attack — the hypothesis correctly identifies the operator as the threat actor. No code guard prevents same-block supply manipulation from affecting the cap calculation.
