### Attack chain: Weight Inflation + Session TOCTOU Bypasses Usage Limits

**Severity (estimated):** High  
**Confidence:** 70%  
**Affected:** recoverBranch, recoverSapientSignature, SessionManager.recoverSapientSignature, ExplicitSessionManager._validateExplicitCall, ExplicitSessionManager._validateLimitUsageIncrement, ExplicitSessionManager.incrementUsageLimit, PermissionValidator.validatePermission

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Attacker targets a session-key-gated operation with usage limits (e.g., max 1 ETH transfer per session). The session requires multi-sig authorization with a specific weight threshold. 2. Attacker inflates the weight of their own signer in the branch signature blob (H2), since weight is not included in _opHash. This allows the attacker to meet the multi-sig threshold alone without other signers. 3. Attacker constructs a batched transaction containing multiple calls that each invoke session-validated operations. During signature validation, SessionManager.recoverSapientSignature() runs as a `view` function (H15). It validates usage limits against current state and computes expected increments. 4. Because the validation is view-only, the usage limit increments are not actually persisted during validation. When the batched calls execute sequentially, each call's actual state update happens after the view validation of subsequent calls. 5. The TOCTOU gap means all calls in the batch see the same pre-batch usage state during validation, allowing the attacker to exceed usage limits by the batch size multiplier. H2 provides the authorization to create the batch; H15 allows the batch to bypass limits.

Chain steps:
  1. recoverBranch: Attacker inflates own signer weight to meet multi-sig threshold alone → Attacker gains authorization to create batched transactions without other signers
  2. SessionManager.recoverSapientSignature (view): Batch of N session-limited calls submitted; view validation checks usage limits for all calls against same pre-batch state → All N calls pass validation since increments are not persisted during view-only check
  3. ExplicitSessionManager.incrementUsageLimit (execution): Each call in batch executes and increments usage limit sequentially → Actual usage exceeds intended limit by factor of N, enabling extraction of N× the per-session limit

Root cause: Unsigned weight in recoverBranch allows meeting threshold with fewer real signers, and SessionManager's view-only validation creates TOCTOU window for usage limit bypass across batched calls
