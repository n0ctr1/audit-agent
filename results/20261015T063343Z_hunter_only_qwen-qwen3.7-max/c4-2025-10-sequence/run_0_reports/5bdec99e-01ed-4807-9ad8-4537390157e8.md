### Attack chain: Chained Signature Checkpoint Bypass via Attacker-Controlled Checkpointer

**Severity (estimated):** Critical  
**Confidence:** 70%  
**Affected:** recoverChained, recover

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Attacker obtains a valid chained signature for a configuration update at a high checkpoint (e.g., checkpoint=100 with a high-threshold multi-sig config). 2. Attacker crafts a new chained signature where the outermost (final) signature has checkpointSize=0 in its flag byte (bits [4..2]=000), causing recoverChained to skip snapshot checkpoint enforcement entirely (H9). 3. For all non-final signatures in the chain, recoverChained passes _checkpointer=address(0) to recover(). When recover() sees _checkpointer=address(0) and flag bit 0x40 is set, it reads the checkpointer address directly FROM the attacker-controlled signature data (H10). 4. Attacker embeds a malicious checkpointer contract address in the signature bytes. This contract's imageHash() function returns whatever imageHash the attacker needs to pass validation. 5. The combined effect — bypassing checkpoint enforcement AND controlling the checkpointer — allows the attacker to forge authorization for any configuration change, including lowering the signing threshold to 1-of-1 and taking full control of the wallet. Neither H9 nor H10 alone achieves this: H9 without H10 still requires a legitimate checkpointer, and H10 without H9 is blocked by checkpoint enforcement.

Chain steps:
  1. recoverChained: Craft chained signature with checkpointSize=0 in final signature flag byte → Snapshot checkpoint enforcement is completely skipped for the final signature
  2. recover (called from recoverChained with _checkpointer=address(0)): Embed malicious checkpointer address in signature data with flag bit 0x40 set → recover() reads checkpointer from attacker-controlled signature bytes instead of using a trusted address
  3. recover (imageHash validation): Malicious checkpointer contract returns attacker-chosen imageHash → Authorization check passes with attacker-forged imageHash, enabling arbitrary config changes like threshold reduction to 1-of-1

Root cause: recoverChained passes address(0) as checkpointer for non-final signatures, and checkpoint=0 skips enforcement, allowing attacker to supply arbitrary checkpointer from signature data
