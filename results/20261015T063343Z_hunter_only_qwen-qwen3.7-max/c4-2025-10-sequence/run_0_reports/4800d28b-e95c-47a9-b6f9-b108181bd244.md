### Unsigned `_metadata` field extracted from signature influences return value (Hash Completeness Violation)

**Severity (estimated):** High  
**Confidence:** 0%  
**Affected:** recoverSapientSignatureCompact, _decodeSignature, _rootForPasskey

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Attacker obtains a valid passkey signature (e.g., by being a legitimate user or observing a prior transaction).
2. Attacker modifies the `_metadata` bytes within the encoded `_signature` calldata. The `_metadata` field is a `bytes32` appended/trailing in the signature encoding.
3. The modified signature is submitted to `recoverSapientSignatureCompact`.
4. `_decodeSignature` extracts the tampered `_metadata` along with the legitimate `_webAuthnAuth`, `_x`, `_y`, and `_requireUserVerification`.
5. `WebAuthn.verify()` succeeds because `_metadata` is never part of the verification — the WebAuthn signature over `_digest` is still valid.
6. `_rootForPasskey(_requireUserVerification, _x, _y, _metadata)` is called with the attacker-controlled `_metadata`, producing a different `bytes32` root than the legitimate signer intended.
7. The returned root is used downstream for authorization, passkey identification, or access control — granting the attacker unauthorized privileges.
