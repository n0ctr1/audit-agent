## Findings Requiring Manual Review

### Chained signature final checkpoint not validated against snapshot in non-chained path

**Severity (estimated):** High  
**Confidence:** 0%  
**Affected:** BaseSig.recover, BaseSig.recoverChained

**Why needs review:** The PoC did not succeed, but the vulnerability hypothesis is plausible based on code analysis. A human auditor must determine whether this is a real issue.

**Attack scenario:** 1. Attacker observes a valid signature with a snapshot (imageHash checkpointer) that has checkpoint=100 and imageHash=X.
2. Attacker crafts a NON-chained signature (flag bits [1..0] = 00) that includes the same checkpointer address and checkpointer data.
3. In `recover()`, the snapshot is fetched: snapshot.imageHash=X, snapshot.checkpoint=100.
4. The attacker sets checkpoint=50 (less than 100) in the signature, and provides a valid signature tree for a DIFFERENT imageHash Y (not X).
5. The final check `if (snapshot.imageHash != bytes32(0) && snapshot.imageHash != imageHash && checkpoint <= snapshot.checkpoint)` evaluates: X != 0 (true) && X != Y (true) && 50 <= 100 (true) → reverts.
6. However, if the attacker sets checkpoint=101 (> 100), the check passes: 101 <= 100 is false → no revert.
7. This means a signature with a HIGHER checkpoint than the snapshot can use a DIFFERENT imageHash, effectively bypassing the snapshot's configuration binding.
8. The attacker can use any valid signature tree (for any configuration) as long as they set a checkpoint higher than the snapshot's checkpoint, potentially authorizing transactions with a configuration that was never approved for this checkpoint range.
